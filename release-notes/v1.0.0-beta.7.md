# Ogoune v1.0.0-beta.7

An incident now tells the truth about the machine it happened on — which machine, and what that machine's agent could actually see. Both were silent gaps: the first rewrote history when a monitor moved, the second made "no kernel events" indistinguishable from "could not have reported any". Both are closed, forward-only.

## What an operator gets

**An incident remembers the machine it happened on.** The host context, the causal sentence and the kernel events on an incident were resolved through the monitor's *current* host. Move a monitor to another machine and every incident it ever had described a machine that was never involved; delete a host and that context vanished. Each new incident now records its machine — or the absence of one — when it opens, and reads from that record afterwards. Incidents from before this release have nothing recorded: they keep showing the monitor's current machine, now with a visible marker saying so, and the API reports `host_link.source` as `recorded` or `inferred` so anyone grouping incidents by machine can tell the two apart. That part cannot be repaired.

**The agent says what it can see.** Kernel-event capture is best-effort and often unavailable — a containerised agent usually cannot read the kernel log, and most machines ship with segfault reporting off — and the only trace was one log line at startup. The agent now checks, before every report, whether it can read the kernel log, the cgroup out-of-memory counter, and whether segfault capture is usable, and declares it. The host page shows it in words:

- *Out-of-memory kills: detected, without the process name* — the container, which stays the recommended install.
- *Segfault capture: unavailable — the kernel is not reporting userspace faults*, with the one-line `sysctl` that enables it, on a native install.

A change on the machine shows within one interval, without restarting the agent — including a source that becomes readable, which the agent starts reading. Each incident freezes the host's declaration when it opens, so a postmortem's "no kernel events" reads as evidence or as a blind spot, and stays that way when the host changes later. Segfault capture is explicitly best-effort; it does not dictate how you install.

**A host page you can read.** The agent reports one entry per filesystem instead of one per mount point. A btrfs root with subvolumes, a ZFS pool, a Docker or Kubernetes node with overlay layers — each produces many mounts backed by one filesystem, all reporting the same capacity. A development VM measured here had 486 mounts over 18 devices; it now reports **3 entries instead of 436**, and makes 3 `statfs` calls per interval instead of 442.

## Upgrading

Two migrations run at startup, both additive and nullable; no row is rewritten. Nothing to configure.

**Upgrade the agent too.** The server accepts older agents unchanged — a host running one shows *this agent version does not report what it can observe* until it is upgraded — and a new agent streams to an older server unchanged. The wire protocol version did not move. The filesystem grouping and the capability declaration both live in the agent, so a server upgrade alone shows neither.

## What contributors get

- `release.yml` no longer runs actions that GitHub forces onto Node 24 with a warning; this release run is the proof.
- The test job gives each package 300 s instead of 120 — the repository package took 117.9 s on a green run and the next one timed out — and the job itself has a 15-minute ceiling.
- The two remaining internal debts are named in `docs/tech-debt.md`. The migration-state one is recorded as a deliberate non-fix.
- A database-health test that failed on the machine rather than on the code now asserts the property instead of a deadline.
