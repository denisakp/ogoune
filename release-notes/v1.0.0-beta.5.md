# Ogoune v1.0.0-beta.5

Incidents explain themselves now.

When a monitor fails on a host running the agent, and that host's kernel reported something in the same few minutes, the incident says so in one sentence — at the top of the page and in the alert that wakes you:

> HTTP check failed: 502 Bad Gateway at 14:03:00 UTC. The kernel OOM-killed postgres (pid 4711) on web-01 at 14:02:47 UTC, 13 seconds earlier.

That completes the observability correlation track: host metrics on incidents, kernel events from the agent, and the sentence that joins them. Database health checks for Postgres and MySQL monitors land in the same release.

## ⚠️ Upgrade if you run the host agent on a machine with many filesystems

Before this release **the server refused every frame from a host with more than a few hundred mounted filesystems** — an ordinary container host or Kubernetes node. A metrics frame carries one entry per mount, and the connection's size limit was left at a default those frames exceed. The agent reconnected every interval forever, the host never came online, and nothing logged why.

Both the agent and the server need updating.

## ⚠️ Security fix

`POST /auth/initialize-password` is unauthenticated by design — it is how an account that has never had a password sets its first one — but it verified nothing beyond the email address existing. Anyone who knew an address could overwrite that account's password and receive a valid session token.

It is now refused for accounts that already have a password. **Upgrade promptly if your instance is reachable from an untrusted network**, and rotate credentials if you have reason to think it was used.

## Highlights

**Incidents that explain themselves**

- One sentence at the top of an incident, and in the notification, when the host's kernel reported something in the same window.
- The rule is a time window and nothing else — the same one the host context uses. No score, no confidence, no "likely cause" label: two things happening close together on one machine is exactly as much as the data knows, and both timestamps are always shown so you can overrule it.
- A storm gets one sentence: it names one event and counts the others.
- Nothing is stored. The sentence is recomputed on every read, so improving the wording improves every past incident, and no field anywhere records a causal claim.
- An incident whose monitor has no host attached costs nothing at all.

**Kernel events from the agent**

- Out-of-memory kills and segmentation faults, read from `/dev/kmsg` and cgroup v2 memory accounting. No eBPF, no kernel module, no extra capability.
- Capture is often unavailable — a container usually cannot read the kernel log — and that path is the normal one: the agent says so once at startup, metrics stream exactly as before, and the cgroup source frequently catches out-of-memory kills anyway.
- Segmentation faults additionally need `debug.exception-trace=1`, which most distributions ship disabled. See the agent guide.

**Database health**

- Postgres and MySQL monitors report connections, longest running query, and replication lag, with every metric independently nullable — absence means the credential cannot read it, not that the value is zero.

**Host metrics**

- Kept at full resolution for longer by default, so an incident opened yesterday still has real numbers behind it (ADR 0011).

## Fixed

Six defects, all found by running the agent on a real Linux host for the first time. None were visible to the test suite, and four were invisible in a container.

- The agent stopped streaming metrics wherever it could read the kernel log — a blocking read on the metrics path.
- The server closed every agent connection from a host with many mounted filesystems, and logged nothing about why.
- Segmentation faults were never captured on arm64, whose kernel uses a different message.
- One out-of-memory kill was reported as three, because two log lines and a counter were added together.
- The causal narrative mixed time zones and stated a gap its own printed timestamps disagreed with.
- The unauthenticated password-initialization endpoint accepted any known email address.

Also in this release: release images build about five times faster, the host agent is documented and enforced as Linux-only, and several documentation drifts left by the root→v1 API convergence are corrected.

## Known limitation

A monitor's host is resolved when an incident is **viewed**, not frozen when it opened. Moving a monitor to a different host changes what its past incidents display — check the host name in the sentence before acting on an old incident.

## Upgrading

No migration to run and no configuration to change. Update the server and the agent together.
