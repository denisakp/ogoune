# Ogoune v1.0.0-beta.6

A correctness release, hours after beta.5. Nothing new to use — the migration machinery, the build guards and the test suite are the things that changed.

Most of it came out of one exercise: verifying the host agent against a real Linux kernel for the first time. That found six defects in the agent work that became beta.5 — all of them fixed before it was published, so no released version was affected — two of which would have meant the agent did not work on the documented native install. Pulling the thread found three more in the migration machinery, one of them in the guard meant to catch the other two.

## What an operator gets

**A migrator that does what it says.** Two things it used to do, and no longer does:

- It executed `.down.sql` files **forward**. Undo scripts were loaded with everything else and run as migrations. It survived only because `.down.sql` sorts before `.up.sql` and the statements are all `IF EXISTS` — the drop hit a table that did not exist yet, then the up created it. Nothing guaranteed that order. On a fresh database it also recorded the name of a down file as the applied migration for **19 of 34 rows**.
- It let two migrations share a version number. Applied state is keyed on the four-digit prefix alone, so a duplicate was indistinguishable from an already-applied migration and the second was skipped — forever, and *only on installs that upgrade rather than start fresh*, which is the hardest shape of that bug to notice: it works on every developer machine.

Startup now refuses a duplicate version, naming both files and the remedy. `0026_report_settings`, which shared its number with `0026_report_history`, is renumbered to `0034`. Every statement in it is `IF NOT EXISTS`, so it re-applies as a no-op on databases that already ran it.

**Nothing to do on upgrade.** A fresh install produces the same tables it did before. A database created by an older Ogoune applies exactly one migration — the renumbered one, as a no-op — and loses nothing. Both verified against real databases, before and after.

## What contributors get

**`make ci-local` can pass.** Two of its nine gates failed on a clean tree, so the command that exists to catch CI breaks before pushing carried no information: you could not tell "I broke something" from "it is the usual noise". `lint-openapi` could not resolve its ruleset, and the OpenAPI drift guard regenerated a contract whose YAML changed on a third of runs. Both fixed; the contract is now byte-identical across regenerations.

**`make migrations-drift-check` inspects the whole tree.** Its filename pattern could not match a name containing a dot, so every `NNNN_name.up.sql` was skipped — 40 of 55 files, including all recent work — while the command reported success. No drift was hiding in them, but the guard had not been looking.

**Kernel capture is verified against a real kernel in CI.** Every previous test exercised the classifier against strings and the collector against a fake source, which is exactly how a blocking read on `/dev/kmsg` reached the release branch before that verification caught it. A CI runner is a virtual machine, so it has the kernel log a container does not: the new job reads it, injects real kernel records and reads them back, and refuses to pass unless the assertions actually ran.

**No compiled binaries in git.** Two were tracked — a 9 MB macOS `agent` and an 8 MB Windows `agent.exe`, both committed by accident. Removed, and a check now fails on anything compiled that reaches the index.

## Upgrading

No migration to run, no configuration to change. If you are on beta.5 or earlier and run the host agent, upgrade both the server and the agent — see the beta.5 notes for why.
